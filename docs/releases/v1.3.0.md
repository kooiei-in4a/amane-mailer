## 3. v1.3.0 implemented scope

The implementation integrated on `develop` before release preparation includes:

- Multiple `To` / `CC` / `BCC` recipients, including Cc-only, Bcc-only, and mixed
  role requests within the documented per-role and aggregate limits.
- Optional / `null` / empty `to` when another recipient role supplies at least one
  recipient.
- Canonical recipient validation, persistence, provider projection, and per-recipient
  delivery-state / provider-event correlation.
- BCC privacy boundaries: SMTP envelope delivery without a MIME `Bcc` header,
  redacted legacy shadow for Bcc-only requests, masked Admin display by default,
  and capability-gated audited reveal.
- Bounded attachments with validation, short-lived spool, provider mapping,
  submission evidence, and fail-closed handling of ambiguous provider outcomes.
- Plain-send submission evidence and `DeliveryUnknown` convergence when provider
  acceptance can neither be proved nor disproved; ambiguous sends are not
  automatically re-invoked.
- The v1.2 plain-send automatic retry loop after provider invocation is removed.
  Once durable `Started` (or later) submission evidence exists, the same request
  never invokes the provider again. Whole-request manual retry / cancel is also
  denied when plain submission evidence exists; a deliberate business resend uses
  a new `mail_request_id` after duplicate-risk assessment.
- All-recipient suppression precheck before provider invocation.
- Canonical payload-hash projection for recipient roles and attachment metadata,
  while preserving baseline single-To / no-attachment hash compatibility.
- Python and TypeScript SDK support for multiple `To` / `CC` / `BCC`, optional
  `to`, and baseline + v1.3 payload-hash vectors.
- Native Docker build paths for `linux/amd64` and `linux/arm64`, Native AOT, and
  setup-bundle generation for the supported host RIDs.

### Compatibility / public-contract notes

- Existing single-To requests without attachments remain valid.
- No public endpoint or existing request field is removed or renamed.
- The recipient and attachment capabilities are additive request-contract changes.
- `to` is no longer required when `cc` or `bcc` provides a valid recipient; all
  three roles empty / omitted is invalid.
- `delivery_unknown` is a public terminal delivery status. Consumers that model
  the status as an exhaustive enum must accept it and must not infer that retrying
  the same delivery is safe.
- **Delivery retry behavior changes in v1.3:** a retryable provider result no longer
  returns a plain request to `Queued` after provider invocation has started. The
  durable submission-evidence boundary intentionally prefers possible non-delivery
  over duplicate provider invocation. This changes operational retry semantics even
  though the HTTP request shape remains backward compatible.

## 4. Migration and upgrade inventory

v1.2.0 released with migrations through `013_provider_queue_dead_letters.sql`.
The v1.2.0 -> v1.3.0 upgrade inventory is, in order:

1. `014_mail_request_delivery_unknown_status.sql`
2. `015_attachment_spool_and_submission_evidence.sql`
3. `016_recipient_persistence_and_plain_submission_evidence.sql`
4. `017_recipient_delivery_events.sql`
5. `018_admin_user_capabilities.sql`

Release qualification must prove both upgrade and fresh-install paths against the
exact candidate. The normal migration runner remains responsible for ordering,
transactionality, checksum verification, and current-schema readiness. `/readyz`
must remain fail-closed when the required schema is missing or a migration checksum
is inconsistent.

### Upgrade procedure / rollback boundary

1. Take and verify a pre-upgrade backup before modifying the v1.2.0 database.
2. Stop or drain the old runtime according to the existing deployment runbook.
3. Apply the exact v1.3.0 candidate/release migrations in numeric order.
4. Start the exact candidate/release runtime and require `/readyz` success before
   routing normal traffic.
5. Verify representative recipient, attachment, and status paths before promotion.

A schema downgrade from migrations 014-018 is **not guaranteed**. Do not attempt to
run a v1.2 binary against a database that has been upgraded to v1.3 unless an
explicit compatibility procedure has been proven. Database rollback requires the
pre-upgrade backup (plus the compatible application/image version) rather than an
assumed reverse migration.

For `DeliveryUnknown`, rollback / recovery must preserve submission evidence. An
ambiguous provider invocation must not be converted into an automatic resend merely
because the application or host is restarted.

1. Release-preparation PR CI is green at a fixed head.
2. Agent B independently reviews that fixed head and returns an acceptable verdict.
3. Maintainer approves the release-preparation result and exact release-execution
   sequence.
4. Generate the v1.3.0 candidate from the approved exact source commit using the
   digest-pinned Mailpit input.
5. Complete exact-candidate qualification, including both native OCI architectures,
   setup bundles, v1.2 upgrade, fresh install, recipient + attachment integration,
   BCC privacy, Mailpit, and artifact checksum/manifest verification.
6. Seal the qualification result and bind it to candidate/source identities.
7. Resolve #504's exact-RC -> `main` promotion/ruleset boundary for this release.
8. Only after the above: perform tag / promotion / NuGet / GitHub Release operations
   in a separately approved release-execution session.
