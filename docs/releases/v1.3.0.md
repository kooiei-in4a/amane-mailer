## v1.3.0 product changes

- Multiple `To` / `CC` / `BCC` recipients, including Cc-only, Bcc-only, and
  mixed-role requests, with per-role maximum 10 and aggregate maximum 20.
- Canonical recipient validation, persistence, provider projection, and
  recipient-level delivery state / event correlation. Duplicate canonical
  addresses are rejected within and across roles.
- Bounded attachments: maximum 5 items, 2 MiB per decoded file, 5 MiB decoded
  total, 8 MiB provider envelope, and 16 MiB consumer HTTP envelope. Allowed
  types are PDF, JPEG, PNG, DOCX, XLSX, CSV, and TXT.
- Durable attachment spool and submission evidence, plus canonical attachment
  metadata in `payload_hash`; raw Base64 is not part of the hash projection.
- Plain and attachment provider invocation now use durable submission evidence.
  Ambiguous acceptance converges to terminal `delivery_unknown`, and the same
  request is not automatically or manually resent after provider invocation
  starts. A deliberate business resend uses a new `mail_request_id`.
- BCC is delivered through the envelope without a MIME `Bcc` header. Standard
  Admin views mask BCC and attachment filename stems; reveal is explicit,
  default-deny, capability-gated, tenant/request/role/ordinal scoped, audited,
  and `no-store`. The Bcc-only legacy shadow is redacted.
- Python and TypeScript SDKs support the recipient roles, optional `to`,
  attachments, and the v1.3 payload-hash vectors.

## Database migration and upgrade

The v1.2.0 to v1.3.0 migration inventory, in order, is:

1. `014_mail_request_delivery_unknown_status.sql`
2. `015_attachment_spool_and_submission_evidence.sql`
3. `016_recipient_persistence_and_plain_submission_evidence.sql`
4. `017_recipient_delivery_events.sql`
5. `018_admin_user_capabilities.sql`

Before upgrading, take and verify a SQLite backup and back up the tenant
configuration according to the operator runbook. Apply migrations through the
normal runner in numeric order, then require `/readyz` to pass before routing
traffic. Readiness is fail-closed when the required schema is missing or a
migration checksum is inconsistent.

Reverse migration across 014-018 is not guaranteed. Rollback requires the
pre-upgrade backup and a runtime compatible with that backup; do not run a v1.2
runtime against a database already upgraded to v1.3. A restart or lease expiry
must not turn durable submission evidence into an automatic resend.

## Operational notes

- `202 Accepted` means that the Mailer persisted the request; it does not mean
  provider delivery completed.
- `delivery_unknown` is a terminal public state for an ambiguous provider
  outcome. Consumers with exhaustive enums must handle it and must not treat a
  retry of the same request as safe.
- HTTP client retry of a retryable `503` is distinct from provider re-invocation.
  After durable submission evidence exists, the Mailer does not invoke the
  provider again for that `mail_request_id`.
- BCC is a sensitive recipient field. Normal Admin display, generic diagnostics,
  logs, metrics, traces, and audit data must not expose raw BCC. Attachment
  filenames are also masked by default in Admin and require an explicit audited
  reveal path.
- Admin remains disabled by default and is intended for internal-network,
  experimental use only.
