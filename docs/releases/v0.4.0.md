## Included changes since v0.3.0

### ACS secret registration CLI (MAILER-ACS-INPUT-01)

- `admin provider register-acs` / `admin provider check-acs-preflight` CLI commands
  (#203): safe interactive registration of the ACS connection string (deploy-time
  secret file, never tenant JSON, never the DB) and a tenant-independent
  platform-owned sender identity file (`platform-sender.json` /
  `platform-sender.schema.json`).
- `mailer-acs-admin` Compose service (profile `acs-admin`) with dedicated read-write
  mounts for the ACS secret and platform-sender directories (#203).
- Two-phase secret write, exclusive cross-process locking, rollback, and review
  fixes (#205, #206).
- `scripts/pty-smoke-register-acs.py` real-PTY smoke test (synthetic values only).

### Staging / Production ACS compose boundary

- `infra/deploy/compose.yml` / `infra/deploy/.env.example`: Staging/Production no
  longer accept bare `ACS_CONNECTION_STRING`; only file-based
  `ACS_CONNECTION_STRING_FILE` (written by `admin provider register-acs`) is
  wired (#203, #204).
- Docs / ops sync: service-spec, SECURITY, README, register-acs runbooks,
  `.dockerignore`, and `validate-tenant-config.mjs` updated for the file-secret path
  (#204).
- Docker Known-gap verification for register-acs mount boundary and UID `1654`
  documented in the register-acs runbook (#206).

### Release docs / default tag consistency

- README, release smoke docs, release smoke scripts, supported-version policy,
  and drift checks aligned on `v0.4.0` defaults.
- CHANGELOG and this release evidence draft prepared for v0.4.0.

### Maintenance

- Dependabot batch on `develop`: GitHub Actions, NuGet, and Docker base image digest
  updates (#207).

The public `POST /internal/mail-requests` HTTP contract shape and acceptance
semantics are unchanged.

## Known limitations

These limitations describe the **`v0.4.0` tagged release**. Later releases
(for example `v0.9.0`) may add status GET, metrics, SDKs, webhooks, or scheduled
send — see the newer release record.

- SQLite deployment assumes a single node / single replica.
- Admin UI remains disabled by default, internal-network-only, and experimental.
- `202 Accepted` means the request was persisted, not that provider delivery
  completed.
- Delivery is at-least-once. If the service stops after provider send succeeds
  but before the database records delivery, the same mail may be sent again.
- No webhook delivery result API.
- No template engine.
- No full multi-recipient support.
