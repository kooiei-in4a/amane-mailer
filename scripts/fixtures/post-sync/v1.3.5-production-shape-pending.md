## Release boundary

v1.3.5 is planned as a **full service release**. The Git tag, GHCR image,
`Amane.Mailer.Contracts` NuGet package, OpenAPI version, CHANGELOG, release
record, and GitHub Release must describe one release version and one frozen
source identity.

The version-preparation branch and PR are not the final release authority. The
exact `releaseCommitSha` is frozen only after the reviewed version-preparation PR
is merged to `main`.

Relative to the published v1.3.4 service source, the changes leading into this
release are Release Engineering tooling, workflows, tests, and documentation.
There is no product feature, runtime semantic, database migration, or public
HTTP contract shape change. The migration inventory remains `001` through `018`.

## Planned publication order

The current normal path is:

```text
frozen main
  -> GHCR v1.3.5 + immutable SHA tag
  -> public image verification
  -> Git tag v1.3.5 at the same releaseCommitSha
  -> Amane.Mailer.Contracts 1.3.5 + symbols from the release tag
  -> GitHub Release v1.3.5
  -> consumer-usable verification
  -> latest promotion to the verified v1.3.5 digest (no rebuild)
  -> prepare-post-sync / current-public authority update
  -> final cross-artifact verification
```

GHCR is first because `.github/workflows/publish-release-image.yml` is bound to
canonical `main` and requires the supplied source SHA to equal the workflow
commit. The release source must not be changed after any public artifact exists.

## Publication invariants

- Do not republish an existing `1.3.5` artifact.
- Do not overwrite or move an existing release tag.
- Do not overwrite GHCR version or immutable SHA tags.
- Do not promote `latest` until versioned publication and consumer verification
  PASS; then promote by digest only (no rebuild).
- Dispatch a publish workflow exactly once; ambiguous dispatch results are
  resolved read-only before any next action.
- Preserve the `release` environment Human approval boundary.
- If image publication succeeds but post-publish verification fails, do not
  republish. Bind the original publication facts and use the existing read-only
  verify-only recovery path.
- Do not advance `release/current-public.json` before verified publication and
  deterministic post-sync.

## Final evidence to record after publication

- confirmation that no same-version republish, tag overwrite, or rebuild-based
  `latest` promotion was used.

Only then may this record change from **PENDING** to **PUBLISHED**.
